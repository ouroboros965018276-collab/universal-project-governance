# 开展、推进与重规划任务

UPG 将 pstack 的接单、调查、规划、可验证单元、阶段检查和重规划融合到既有工作流。语义只在[规范模型](../governance-src/model/governance-model.json)维护；本页说明[生命周期](../governance-src/runtime-scripts/project_tool.py)及[任务契约](../governance-src/runtime-scripts/task_lifecycle.py)的输入，不建立另一个任务系统。

所有维护任务都先按比例明确用户结果、范围、保留契约、可观察验收、当前事实和关键未知。局部低风险工作可以是一句目标和一个验证单元；不因此要求计划审批或新建文档。有 helper 时，非平凡、需要跟踪或跨会话工作使用 `begin`，过程与结束仍通过同一工作流的 `finish`，报告开关保持原选择。没有 helper 时，在已有项目计划、记录和交接中承接相同语义，明确未运行的机械校验；不伪造文件，也不阻塞无关且已授权的工作。

## 开始

先检查实际入口、项目约定、当前状态、差异和既有验证，再沿契约与真实消费者调查。可观测未知可用便宜的只读检查或隔离实验解决；调查本身可以是第一个单元。只有实质决策、约束或权限缺口才阻塞相关行动，独立且已授权的工作可继续。

新 `begin` 在原 `workflow_id`、`change` 外要求 `task_contract`。`change.function` 继续表示原始目标，不另存一份目标。契约包含当前初始计划身份、作用域、可观察验收、约束、明确未知，以及有依赖的可验证单元。每个单元描述结果和检查方法；实际并行共享写入时可标注 `owner`，它不证明账号身份或授予权限。

例如，下列只是原开始输入中的新对象；原 `change` 必填字段仍按[报告契约](../governance-src/schemas/field-report.schema.json)提供：

```json
{
  "task_contract": {
    "revision": "p1",
    "scope": ["修复已确认的入口及受影响消费者"],
    "acceptance": ["原失败输入通过；已知正常输入行为保持"],
    "constraints": ["保留既有公开接口与权限"],
    "unknowns": ["先确认实际错误发生在哪个消费者"],
    "units": [
      {
        "id": "diagnose",
        "outcome": "复现并定位错误及影响范围",
        "verification": "读取实际入口并运行可区分假设的检查",
        "depends_on": []
      },
      {
        "id": "repair",
        "outcome": "原因修复且受影响行为通过",
        "verification": "失败前与通过后的真实行为回归",
        "depends_on": ["diagnose"]
      }
    ]
  }
}
```

单位身份唯一，依赖必须存在且不能成环。机械小任务可只有一个单元；较大重复批次先用首个真实单元检验任务说明、验证配方和单位大小，再扩大执行。不要为了填满表格编造已知事实、依赖、负责人或验收。

已有当前项目 JSON 可通过顶层 `current_state: {"path": "项目内相对路径", "sha256": "实际当前哈希"}` 引用；开始接受前校验引用。它不是另一份计划，也不表示 JSON 内容的语义已获证明。工程记录使用现有 `execution.schema.json`，不要把 field report 输入直接当成 `execution/latest.json`。

## 推进

每个单元按目标或假设、有限行动、当前产物检查、观察结果和下一行动推进。失败、不确定、缺席的代理结果或未覆盖的切片不能满足依赖。独立单元仍可继续；系统性基线失败时先停止受影响下游。委派结果要核对实际产物、来源修订和覆盖，晚到结果也要对账。

新契约工作流的阶段结果携带 `task_progress`，仍使用 `partial` 或 `blocked` 与稳定 `checkpoint_id`。结果精确覆盖当前计划中的所有单元，完成前按原验收提供证据。`next_action` 表示尚未结束时具体的下一步；完成必须为 `null`。

```json
{
  "task_progress": {
    "revision": "p1",
    "results": [
      {"id": "diagnose", "status": "running", "evidence": []},
      {"id": "repair", "status": "pending", "evidence": []}
    ],
    "acceptance": [],
    "next_action": "运行能区分两个候选原因的已确认入口"
  }
}
```

`passed` 需要非空的实际观察说明，以及至少一种当前来源：`sources` 的文件/删除/模式身份、有效 `current_state`，或既有规范运行的 `validation_ref`。文件身份格式与[完成审查](completion-review.md)相同；验证引用复用既有运行 ID、SHA、范围与待重测语义。未通过、仍运行、`pending_retest` 或存在后续改动的运行不能证明通过。字段限制和枚举以安装包 schema 与运行时为准。

结构和哈希仅校验记录一致性。真实执行、因果关系、检查覆盖及语义正确性仍由实际工具结果、负责人和审查证明。`status.ok` 表示治理状态健康，不能解释为任务准备充分或已完成。

## 重规划与交接

新约束、消费者、错误前提、失效证据、工具或代理失败、预算边界会触发重新核对。反复失败时先检验共同前提；不确定的业务写操作先核对状态再重试。只调整受影响的余下计划，记录新修订、前一修订和原因；不能悄悄降低原验收、扩大授权或倒改开始事实。

`task_progress.replan` 包含 `from_revision`、实际 `reason` 和完整的新 `units`。仍有效的已成功单元定义保留；证据失效时通过 `invalidation_reason` 明确降级，该单元及受影响依赖回到待处理前沿。下一边界可有依据地重规划已失效单元，再以实际新证据通过；独立有效结果保持。原始契约与历史观察不倒改；报告关闭时不声称保留了完整逐阶段历史。当前计划与结果继续放在既有 `last_outcome`，原计划是开始快照，不形成第二当前真相或进度账本。

在有意义阶段边界保留当前前沿、阻塞和下一行动。预留验证、审查及交接预算；跨会话或未完成转移时更新现有 handoff。中断后先核对当前源码、差异、运行证据和交接，缺失历史意图保持未知。`compact` 保留被绑定当前引用或既有验证引用保护的记录；引用失效时先协调，不能自动删掉它。

## 完成与兼容

新契约工作流必须满足原任务验收、所有当前必要单元的通过证据，再经过 RC20.9 的最终字节审查/审计门禁。通过后续证据不能追溯证明更早开始时已知。局部审查不证明全项目无债务；外部阻塞保持有界事实。

已存在且没有新契约的活动工作流、历史读取和原输入的精确重试保留原事实，不补造历史计划。没有活动工作流的直接 field report 继续用于观察记录，仍须完成审查；它不能携带新任务契约/推进数据假称已观察过开展过程。实际跟踪任务必须开始并通过同一生命周期推进，不能以观察接口替代。

任务契约不增加模型调用、审批、额外存储或进程。Git 检查点仍按已显式启用的范围运行；推送、合并和外部操作沿用现有授权，报告选择和资格标准保持原契约。实际验收分别记录规范生成、行为回归、CI、安装字节、官方发现和已安装脚本调用，不能互相代替。
